# Shared SHA-256 acceleration

The canonical input fingerprint and durable-file receipt hash share the
whole-block compressor in `core/io/sha256_blocks.h`. On x86-64 with GCC or Clang,
`X86Blocks` uses SHA-NI, SSSE3 and SSE4.1 intrinsics. Its function target enables
only those extensions; project-wide compiler flags remain unchanged. Cached
CPUID checks require all three features before the dispatcher enters it.
Unsupported CPUs retain `PortableBlocks`; the existing ARMv8 SHA2 path is
unchanged. This adds no library dependency, including to `GLAMDB_IO_ONLY` builds.

The state permutation and message schedule follow Jeffrey Walton's
[public-domain intrinsics implementation](https://github.com/noloader/SHA-Intrinsics/blob/master/sha256-x86.c),
based on Intel's and Sean Gulley's examples. The
[Intel SHA extensions description](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sha-extensions.html)
explains the ABEF/CDGH state layout and schedule instructions. The implementation
uses the existing constants and four-vector rolling schedule rather than a new
hash provider or a separately maintained unrolled constant table.

Only block compression and its dispatcher change. The algorithm/version,
canonical preimages, wrapper layouts, incremental updates, padding, byte-count
and overflow handling, const finalization, persisted hashes and receipt formats
remain unchanged. The compressor keeps fixed local state and does not allocate.
As before, internal callers supply a valid eight-word state separate from input;
a zero block count permits null input, not a null state.

## Reproduce

With the ordinary pinned native dependencies and toolchain configured:

```sh
cmake --build build/release --target glamdb_sha256_bench glamdb_bulk_ingestion_bench
build/release/tests/glamdb_sha256_bench > sha256.csv
```

`glamdb_sha256_bench` hashes a prebuilt, unaligned 16 MiB binary stream through
both wrappers, with 64-byte, 4 KiB and 1 MiB updates. Every shape gets one warm-up
and five measured trials; every digest is checked against a literal independently
computed with Python `hashlib`. CSV reports wall time, process CPU time and
ordinary C++ allocation calls on the benchmark thread. This counter excludes
direct `malloc`, aligned allocations, and input generation. Each wrapper includes
its existing hexadecimal digest string allocation.
Builds with ASan, TSan, MSan or LSan leave allocation hooks to the sanitizer and
report `unavailable` in the `cpp_allocations` column; digest checks still run.

The native ingestion benchmark's `ordinary` profile measures real
`AppendDurable` calls with generated Arrow batches, file production and durable
publication. Use a new canonical absolute `ROOT` and `LEDGER` for every trial:

```sh
# Narrow: 128 one-row appends, 16-byte string payloads.
build/release/benchmarks/glamdb_bulk_ingestion_bench \
  ingest ordinary ROOT LEDGER 128 16 1
# Wide: 64 appends of 16 rows, 64 KiB string payloads (64 MiB total payload).
build/release/benchmarks/glamdb_bulk_ingestion_bench \
  ingest ordinary ROOT LEDGER 1024 65536 16
# A different binary can reopen the same unchanged store and retry its first operation.
build/release/benchmarks/glamdb_bulk_ingestion_bench \
  reopen ordinary ROOT LEDGER ROWS PAYLOAD_BYTES CHUNK_ROWS
```

The fixture checks literal generated rows, duplicate keys, initial and historical
views, permanent receipts, and exact retry without external-file I/O or a new
snapshot. `ingest_ms` excludes subsequent verification. Whole-process CPU/wall
and RSS, when measured externally, include creation, verification and shutdown;
they must not be described as append-only CPU. Shared memory peaks are reservation
accounting, not allocator totals or measured RSS. This fixture does not reproduce
the longer retained-history campaign in issue #175.

## Executed validation (2026-11-12)

Environment: Linux x86-64/ext4, AMD EPYC 7713 with `sha_ni`, Clang 18.1.3,
libc++ 18, Release `-O3 -DNDEBUG`, no global ISA flags; shared host. Baseline is
`31a8db6` with its unmodified portable compressor. Both native variants use the
same dependency prefix and workload source. Operating-system caches are retained.
These controlled measurements were collected before refreshing the PR base to
`ad898d7`; the final source is also checked against that newer base.

- The acceleration regression fails on the original implementation and passes
  with this change. The original I/O unit suite passed 179 tests; the updated
  suite passes 182 tests.
- Direct portable and accelerated tests check independent digest literals and
  padding boundaries, all 16 byte alignments, non-SIMD-aligned states, arbitrary
  chaining states, canaries, split block calls and zero blocks. Existing wrapper
  tests cover binary data, arbitrary update splits, sizes and repeated const
  finalization followed by more input.
- QEMU x86-64 Nehalem, SHA without SSSE3, and SHA without SSE4.1 each pass ten SHA
  tests and skip the accelerated-only test. The executable retains its SHA
  instructions, demonstrating runtime fallback rather than an ISA-free rebuild.
- A Clang 18 AArch64 build with an Ubuntu cross sysroot passes all eleven SHA
  tests under QEMU, including direct ARM SHA2 and portable paths. This checks
  correctness; it does not establish native ARM throughput.
- Strict ASan/UBSan SHA checks pass all eleven tests with leak detection disabled
  because this environment prevents LSan's ptrace-dependent inspection. Seven
  unrelated exception tests in the complete I/O sanitizer suite report
  `operator new`/`free` mismatches inside the prebuilt libc++abi exception handling.
  The full 182-test I/O suite passes with
  `ASAN_OPTIONS=detect_leaks=0:alloc_dealloc_mismatch=0`. That workaround is not
  used for the strict SHA checks and is not a sanitizer configuration change.
  A standalone program that only throws/catches `std::invalid_argument` reproduces
  the mismatch without any engine, SHA or test-framework code. Affected tests:

  - `DurabilityTrace.ExplicitBaselineAnchorsKnownDurableAncestors`
  - `FaultRules.RejectInvalidSchedules`
  - `IoAttempt.ExceptionUnwindingReleasesTheReservation`
  - `SourceFailures/TCopySourceFaultTest.SourceMutationOrExceptionCannotYieldReceipt/1-byte object <03>`
  - `SourceFailures/TCopySourceFaultTest.SourceMutationOrExceptionCannotYieldReceipt/1-byte object <05>`
  - `SourceFailures/TCopySourceFaultTest.SourceMutationOrExceptionCannotYieldReceipt/1-byte object <06>`
  - `WriterExceptions/TWriteExceptionTest.OriginalExceptionIsRecordedBeforeReservationCleanup/4-byte object <05-00 00-00>`

- A fresh reviewer independently checked digest literals with `hashlib` and
  exercised input/state at guard pages, 16-thread concurrent initialization,
  multiple translation units and LTO. Clang 18 O0/O3 and O3+LTO, GCC 13 O3+LTO,
  and Clang ASan/UBSan harnesses passed. GCC 13 was a header compatibility check,
  not the project's required GCC 14 full build. Disassembly confines the added
  instructions to the targeted function.
- LLVM 18 formatting and quality negative checks pass. Changed test/benchmark
  translation units pass the configured clang-tidy checks.

## Full native suite and baseline exceptions

The first full native run used:

```sh
GLAMDB_REQUIRE_NATIVE_CLIENTS=1 GLAMDB_VALIDATE_SCHEMAS=1 \
  ctest --test-dir build/release --parallel 4 --output-on-failure --no-tests=error
```

Of 1,088 discovered tests, 1,071 passed, 11 skipped their explicit manual/child
profiles, four were disabled, and these two failed:

- `glamdb.unit.TDecimalDateWriterTest.AppliesNativePlainAndDateIntegerEncodingsWithExactRoundTrip`:
  the installed writer rejects plain encoding for decimal column `amount`.
  A baseline executable linked to the saved, unmodified core/I/O archives fails
  identically. The SHA optimization does not change encoding settings or writer code.
- `glamdb.unit.IcebergMetadataJsonCost.SerializationIsLinearInRetainedSnapshots`:
  the parallel run measured ratio 3.26 against a limit of 3.0. Isolated runs pass
  with the original compressor (2.35) and accelerated compressor (2.39). This
  timing-only test does not call SHA and its source is unchanged.

After refreshing to official `ad898d7`, the same complete command discovers
1,091 tests: 1,075 pass, 11 skip, 4 are disabled, and the one confirmed
baseline decimal-encoding test fails identically. The metadata timing test passes.
No new failure was introduced by the SHA change; the complete suite is not
reported as green. Baseline failure evidence comes from an executable relinked
with the saved original compressor/core archives and the same dependency prefix.

The full suite includes real native write/recovery/fault tests, SDK HTTP/TLS,
installed-consumer reopen, native bulk/capacity checks and public facade scans.
The independent I/O-only CTest run passes all 183 tests, including its tooling
checks, without engine/Arrow/Iceberg/SQLite/OpenSSL hash dependencies.

## CPU-only measurements

To reduce scheduler variation, three cycles rotated baseline, accelerated and
forced-fallback binaries, each pinned to logical CPU 0. Each invocation keeps
the benchmark's warm-up and five trials, giving fifteen measured trials per
shape/variant. Tables show medians. These are shared-host observations, not an
end-to-end append speedup claim.

| Wrapper | Update bytes | Portable MiB/s | SHA-NI MiB/s | Portable CPU ms | SHA-NI CPU ms | C++ allocations, before/after |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| io | 64 | 152.0 | 865.3 | 105.30 | 18.50 | 1 / 1 |
| io | 4,096 | 144.9 | 967.0 | 110.40 | 16.55 | 1 / 1 |
| io | 1,048,576 | 135.5 | 983.6 | 118.13 | 16.27 | 1 / 1 |
| canonical | 64 | 138.5 | 834.8 | 115.53 | 19.17 | 1 / 1 |
| canonical | 4,096 | 131.9 | 937.6 | 121.25 | 17.07 | 1 / 1 |
| canonical | 1,048,576 | 147.3 | 965.9 | 108.64 | 16.57 | 1 / 1 |

Every measured trial produced the exact independent digest. The single counted
allocation is the existing hexadecimal result string; compression adds none.
The fixed wrapper sizes and resource ownership contracts are unchanged.

For a native fallback comparison on this SHA-capable CPU, a benchmark-only
preincluded CPUID adapter cleared `bit_SHA` through a volatile mask before the
unchanged cached gate examined it. There is no production override or mutable
dispatch control. The resulting portable throughput was:

| Wrapper | 64-byte updates | 4 KiB updates | 1 MiB updates |
| --- | ---: | ---: | ---: |
| io | 150.8 | 152.7 | 152.2 |
| canonical | 152.9 | 155.1 | 159.0 |

Units are MiB/s. The gated fallback shows no material throughput regression in
this pinned comparison. Its small increases are measurement/code-layout effects,
not a change to portable compression. Unpinned and emulated timings varied more;
QEMU results above establish correctness rather than native throughput. No
physical ARM performance measurement was run.

## Native append measurements

Each variant/shape ran in a fresh disposable store, with one warm-up followed by
five measured trials. Baseline/accelerated order alternated. Medians below exclude
warm-up. Ingestion wall time covers batch generation through durable append
acknowledgment, including the evolving retained history. Process CPU includes
all fixture verification and shutdown, as measured with `wait4`; it is a
separate scope from ingestion wall time.

| Shape | Variant | Ingestion wall ms | Whole-process wall ms | Whole-process user ms | Whole-process system ms | Peak RSS MiB |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| narrow | baseline | 4736.2 | 24010.2 | 19837.6 | 934.5 | 30.7 |
| narrow | accelerated | 4714.3 | 22795.8 | 18652.9 | 937.1 | 30.7 |
| wide | baseline | 4099.2 | 8677.9 | 6475.3 | 345.4 | 38.9 |
| wide | accelerated | 2761.8 | 7504.0 | 5741.7 | 327.3 | 39.1 |

The wide fixture improves ingestion wall time by 32.6%. The narrow
fixture has no meaningful wall-time improvement beyond observed host variation.
These measured shapes do not promise the same gain for other append sizes or
retained histories. The data reservation peak is identical between
variants: 256.1 MiB for narrow and 261.1 MiB for wide. Metadata reservation peaks
remain about 892 MiB (narrow) and 890 MiB (wide), with unchanged class limits.
Actual RSS is shown separately above. No input-sized compressor allocation or
new reservation owner is introduced.

All trials pass the fixture's row/view/receipt/retry checks. For one measured
store of each shape/variant, the opposite binary also passed a fresh-process
reopen and exact retry against the original ledger: old-to-new and new-to-old.
No migration or hash/receipt version change is required.

## Review and alternatives

The independent review found no actionable defect. It checked CPU gating,
unsupported instruction isolation, state/feed-forward/schedule correctness,
alignment and bounded accesses, zero/multiple blocks, thread-safe initialization,
header ODR, fixed memory use and unchanged wrapper/persistence contracts.
Cross-version reopen and exact retry provide additional integration evidence;
normal storage and fault suites remain the authority for publication failures.
This optimization does not qualify physical power-loss durability.

A separate x86 translation unit would reduce intrinsic-header exposure but add
build/linkage machinery to the existing header-local ARM design. Cached function
pointer dispatch and an unrolled kernel remain possible later optimizations if
measurements justify their extra maintenance. A production OpenSSL provider would
add a dependency to the independent I/O layer. Keeping one shared compressor
avoids divergence between payload fingerprints and durable-file receipts.
