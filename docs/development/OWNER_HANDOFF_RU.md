# Контекст и передача владельцу проекта

Реализована автономная часть участника 4: golden fixtures и независимые
проверки, инструменты fault-evidence, сетевой Python SDK и розовый UI.
Отсутствующие зависимости участников 1–3 заменены явным disposable mock.
Это решение следует указанию замокать ещё не реализованные зависимости;
настоящее C++-хранение не было заменено вторым Python writer.

## Что можно использовать сейчас

Из корня репозитория выполните команды из [WORKBENCH.md](WORKBENCH.md).
UI работает на http://127.0.0.1:8765; токен задаётся в GLAMDB_TOKEN и вводится
в форме подключения. Можно создавать коллекции, добавлять JSON-строки,
смотреть точные int64, фильтровать, выгружать Arrow, выбирать исторические
снимки и смотреть схему, статистику, файлы, Explain и исходы операций.
Перезапуск mock-сервера удаляет все его данные.

Дизайн — фуксия и другие розовые оттенки, бантики, искорки, губки.
Цвета, основные размеры, шрифты, скругления, тени, бренд, основные тексты
и украшения вынесены в `ui/config/theme.json`. Изменения подтягиваются
примерно за две секунды без пересборки и перезапуска. Есть Style studio
с предпросмотром и выгрузкой JSON. Оставшиеся мелкие правила в CSS тоже
редактируются без компиляции. Секреты в браузерное хранилище не записываются.

## Принятые допущения

- Текущая стадия — append v0 из переработанного RFC. Дубликаты ключей
  сохраняются; upsert, delete, compaction, jobs, S3 и schema evolution выключены.
- Backend, SDK и проверяющие инструменты написаны на Python, существующее
  ядро остаётся C++. Для браузера использованы HTML/CSS/ES modules: это
  позволяет менять оформление без сборки frontend или бинарника.
- Формы `/v0` для коллекций и сканов — документированный предварительный
  контракт адаптера. Его надо согласовать с реальным facade, когда он появится.
- Theme-конфиг меняется оператором на диске. UI делает локальный preview
  и download, но не получает привилегированную ручку записи файлов сервера.
- UI хранит исходы операций только до перезагрузки вкладки. Для восстановления
  между запусками приложение должно сохранить исходные UUID, схему и payload;
  SDK принимает идентификаторы вызывающего приложения и сам новые не выдаёт.

## Возникшие проблемы и решения

- Среда запрещала localhost-сокеты в sandbox: интеграционные тесты запущены
  с разрешённым доступом, без автоматического пропуска тестов.
- CUA browser host был недоступен. Использован настоящий Chromium через
  Playwright; сценарии кликают UI, снимки экрана просмотрены визуально.
- Playwright installer завис на распаковке Chromium под Node 26. Официальный
  ZIP проверен и распакован системным unzip; в тестах использован документированный
  GLAMDB_BROWSER_PATH. Абсолютный путь этой машины в репозиторий не добавлен.
- Недостающие Ninja и LLVM 18 установлены в локальную venv. Настройки
  системного компилятора и C++-зависимости не менялись.
- Проверки и ревью обнаружили гонки старых ответов сканов/статусов, потерю
  pending-операции при работе с другой коллекцией, чужой статус в новом
  диалоге, потерю ответа create и зависание формы при занятом имени.
  Для них добавлены регрессионные тесты и исправления.
- SDK принимал неправильный hash/version в receipt: добавлены проверки
  канонического хеша исходного запроса и негативные тесты.
- В закреплённых внешних пакетах остаются предупреждения Starlette TestClient
  о httpx и Node 26 о deprecated API. Тесты проходят; предупреждения не скрыты.
- HTTPS push через OAuth был отклонён из-за отсутствия scope workflow.
  Существующий SSH-доступ сработал, весь CI-файл опубликован. Для origin
  этого репозитория настроен SSH push; глобальная конфигурация Git не менялась.

## Что ещё требует настоящего ядра

Нельзя утверждать, что готова вся БД или пройдены G1–G4. Не реализованы
настоящий Parquet writer/reader, Iceberg/catalog publication, SQLite recovery,
реальное pruning, restart/reopen, durable receipts и физическая power-loss
квалификация. Файлы/row groups в UI синтетические; неизвестные байты остаются
null. Модель fault ordering предполагает атомарный durable catalog commit
и не моделирует SQLite journal/pages целиком.

После появления участников 1–3 нужно подключить один C++ write authority,
сверить контракт, прогнать golden/metrics fixtures на настоящих файлах,
повторить SDK/UI roundtrip и T-HANDOFF, затем выполнить process-crash и
qualified Linux/ext4 power-тесты на отдельном устройстве. Рабочий пользовательский
том для destructive tests не использовался.
